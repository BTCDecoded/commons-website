How to read this page
  • Code-health figures are sizes and counts, not grades.
  • Assurance radials score yes = 2, partial = 1, and not found = 0. A not-measured or n/a cell is a gap or hatch, never a zero. A missing spoke is not a weak score.
  • "Not found" means no public source turned up. It does not mean the project lacks the thing.
  • Every numeric cell is dated (this reading: 2026-11-12) and pinned to a commit. Sources open under the row. Author and release counts use the 12 months from 2025-11-12 to 2026-11-12.
  • Rules share uses three different cuts. Those percentages are not comparable across cuts. Several rules-share cells are not measured, including BLVM's.
  • Size and composition tables cover 9 trees. Floresta, rbitcoin, and btcd appear in the other tables but have no size row.
  • Some checkouts are shallow. Process figures for Bitcoin Core come from cited research reports and are not scored this week for the H2–H6 rows.
  • The implementation is called BLVM. "Bitcoin Commons" names the written governance rules, which are in Phase 1: enforcement is off and the keys are test keys.
  • No chart or caption on this page claims a full-chain differential result.
Glossary

Independence

Lineage (Core-derived vs separate codebase)
What: Whether the tree is Bitcoin Core, is stated as built from Core or from Bitcoin Knots, or is a separate codebase. Why: Clients that share a lineage can share a bug. Moving to a Core-derived client can change policy without changing the code underneath. How: Derived from data/implementations.json class and governance.history, as quoted by scripts/ecosystem-charts/10-lineage.mjs on pull request #6. Four rows are the Satoshi lineage: Bitcoin Core; Bitcoin Roots, a patch series on Bitcoin Core v32.1 that also carries selected Knots policy features; Knots Legacy, which continues Bitcoin Knots v29.3.knots20260507; and Bit-Block, a fork of Bitcoin Knots v29.1.knots20250903. Bitcoin Knots itself is not a row on the page. The other eight rows have no derivation from Core or Knots stated in the data and are grouped by primary language from data/stack.json languages. Caveats: "Separate" means no derivation is stated in this page's data. rbitcoin carries Bitcoin Core as a git submodule (stack.json vendored); that is not counted as a derivation. Assurance

Formal spec
What: A written, formal consensus specification separate from the code. Why: Without a spec to check against, an alternative has to copy Core's behavior from Core, which keeps it tied to Core. How: Qualitative reading of each project's public repository, with a source link on yes or partial cells. Caveats: On this reading, only BLVM is yes (the Orange Paper, with a Lean model of part of it). Hornet is partial. The rest are not found. A not-found cell is not a claim that no spec exists. Open the table: Formal spec
Test vectors
What: Conformance against shared test vectors, such as Bitcoin Core's JSON vectors. Why: Shared vectors are a common check that two implementations accept and reject the same cases. How: Public-repository reading, with a source link. This is a yes/partial/not-found status, not the file count in the metrics table. Caveats: "Yes" does not mean every vector file is run, or run to completion. BLVM runs every committed script and transaction row, and skips a row only for a named reason. libbitcoin and rbitcoin are partial. Hornet is not found. Open the table: Test vectors
Property tests
What: Property-based tests (proptest, quickcheck, and similar). Why: They check general rules over many generated cases, not only fixed examples. How: Public-repository reading, with a source link. Distinct from the test_property line-count in metrics.json. Caveats: satd and btcd are partial. Most Core-family rows are not found. Open the table: Property tests
Fuzzing
What: Fuzz targets in the tree. Why: Fuzzing feeds unexpected inputs to consensus and protocol code. How: Public-repository reading, with a source link. The yes/partial status is separate from the numeric metrics.json fuzz_targets count (see Code health). Caveats: btcd is partial. libbitcoin and Hornet are not found. Core-family yes cells include fuzz harnesses carried from Core. Open the table: Fuzzing

What: Machine-checked proofs or model checking of code. Why: A proof can show that a function or a sentence of a spec holds, beyond passing tests. How: Public-repository reading, with a source link. Open the table: Formal verification

What: a checklist of what a release line needs to count as stable, one segment per criterion: met, not met, or not measured. Why: a node that changes under you, or has no release to pin, can drift from the network. How: Score = met / total criteria, with not measured counted in the total so it never inflates a score. Why the ecosystem matters

Bitcoin is a commons

Anyone can run a node, transact, or mine. The code most of the network runs is a commons too: many depend on it and no one owns it. Elinor Ostrom found that commons last when their rules are visible, the people bound by the rules take part in changing them, those who decide answer to the people affected, and exit is real rather than theoretical. A commons without those properties runs down.

One lineage runs the network

On November 12, 2026, about 90% of reachable nodes advertised Bitcoin Core and about 9.5% advertised Bitcoin Knots (Coin Dance, Bitnodes via 21btc). That Knots count is one user-agent family that mixes releases from before and after the split, and no crawler reports Knots Legacy, Bit-Block, or Bitcoin Roots on its own. Clients in the Knots line share about 95% of Core’s code, so about 99% of reachable nodes ran one code lineage. A flaw travels with the lineage that carries it: the 2018 inflation bug hit Core and Knots alike. Moving to a Core-derived client changes policy, not the code underneath, so it shows demand for an alternative rather than diversity. The structural fix is several independent implementations, each proven to enforce the same rules, under different governance models.

What this page measures

An independent node only helps if it can show it enforces the same rules as everyone else. Without a written consensus spec, an alternative has to copy Core’s behavior from Core, which keeps it tied to Core. The engineering answer is a stack: a spec to check against, then formal verification, fuzzing, differential testing against Core, and property tests. Every reading is dated and redone periodically. Governance labels and the rules share are qualitative readings.

commons
Every node implementation built for Bitcoin only and roughly compatible with the Bitcoin network, whether written from scratch or forked from Core. No altcoins. Its health is what this page measures.
Commons governance
Written rules for how node software changes, published by Bitcoin Commons following Ostrom’s principles: signatures by repository layer, review periods, and a governance-node quorum. The rules are built into BLVM and can be forked or adopted by other projects. BLVM is the only implementation here that uses them, and enforcement is not on yet.

Further reading: the Bitcoin Commons white paper, Who Governs Bitcoin’s Code, Making Core Irrelevant, and Why Bitcoin Needs a Specification.

How these are counted

Languages: those with 5% or more of code lines (tokei 14; .h headers count with C and C++). Direct dependencies: direct third-party libraries of a default node build, excluding build tools, test and dev dependencies, off-by-default extras and the project's own crates; vendored source is counted separately; no transitive counts. C++: libraries the default bitcoind (or node binary) links, minus Qt and native build tools. Rust: third-party crates reached from the node binary through its own workspace crates, with default features (cargo tree). BLVM is the exception: the same count on the minimal release (`--no-default-features --features minimal`), not default features. Go: go.mod require lines not marked indirect. Every row was counted on a separate checkout at its pinned commit. Vendored: library subtrees or vendor/ directories in the tree, with their code lines rounded.

Forms

These cards are the codebook from Bitcoin Has Governance. Each score is a judgment of a form, not a measurement of a tree. The order is the article's. A higher total is not a rank of the implementations above.

Capture resistance
The smallest set of actors whose assent changes the rules, and how concentrated merges are.
Exit cost
The share of economic weight that followed a fork. A higher score means leaving is cheaper.
Legibility
A named decider, and a written rule for who decides. Neither part scores 1. One part scores 2 or 3. Both score 4 or 5.
Error correction
Time from a bad decision to a rollback, and who had to agree.
Credible commitment
How many veto players there are, and how far apart they sit.
Decision cost
Time from proposal to decision. A higher score means the decision is cheaper.
