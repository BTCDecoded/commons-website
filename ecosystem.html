Why the ecosystem matters

Bitcoin is a commons

Anyone can run a node, transact, or mine. The code most of the network runs is a commons too: many depend on it and no one owns it. Elinor Ostrom found that commons last when their rules are visible, the people bound by the rules take part in changing them, those who decide answer to the people affected, and exit is real rather than theoretical. A commons without those properties runs down.

One lineage runs the network

On November 12, 2026, about 90% of reachable nodes advertised Bitcoin Core and about 9.5% advertised Bitcoin Knots (Coin Dance, Bitnodes via 21btc). That Knots count is one user-agent family that mixes releases from before and after the split, and no crawler reports Knots Legacy, Bit-Block, or Bitcoin Roots on its own. Clients in the Knots line share about 95% of Core’s code, so about 99% of reachable nodes ran one code lineage. A flaw travels with the lineage that carries it: the 2018 inflation bug hit Core and Knots alike. Moving to a Core-derived client changes policy, not the code underneath, so it shows demand for an alternative rather than diversity. The structural fix is several independent implementations, each proven to enforce the same rules, under different governance models.

What this page measures

An independent node only helps if it can show it enforces the same rules as everyone else. Without a written consensus spec, an alternative has to copy Core’s behavior from Core, which keeps it tied to Core. The engineering answer is a stack: a spec to check against, then formal verification, fuzzing, differential testing against Core, and property tests. The table below tracks that stack, plus shared test vectors, for each implementation, next to who governs it. The sections after it count the code and read each project’s written rules. Every reading is dated and redone periodically. Governance labels and the rules share are qualitative readings.

commons
Every node implementation built for Bitcoin only and roughly compatible with the Bitcoin network, whether written from scratch or forked from Core. No altcoins. Its health is what this page measures.
Commons governance
Written rules for how node software changes, published by Bitcoin Commons following Ostrom’s principles: signatures by repository layer, review periods, and a governance-node quorum. The rules are built into BLVM and can be forked or adopted by other projects. BLVM is the only implementation here that uses them, and enforcement is not on yet.

Further reading: the Bitcoin Commons white paper, Who Governs Bitcoin’s Code, Making Core Irrelevant, and Why Bitcoin Needs a Specification.

How these are counted

Read at each pinned commit. License: the repository's license file; no proprietary or non-OSI license file turned up in any tree. Languages: those with 5% or more of code lines (tokei 14; .h headers count with C and C++). Direct dependencies: direct third-party libraries of a default node build, excluding build tools, test and dev dependencies, off-by-default extras and the project's own crates; vendored source is counted separately; no transitive counts. C++: libraries the default bitcoind (or node binary) links, minus Qt and native build tools. Rust: third-party crates reached from the node binary through its own workspace crates, with default features (cargo tree). Go: go.mod require lines not marked indirect. Every row was counted on a separate checkout at its pinned commit. Vendored: library subtrees or vendor/ directories in the tree, with their code lines rounded.

Who may change the rule
Tiers and layers are written. When a layer and a tier both apply, the more restrictive pair wins. Two Tier 5 pairs are both written. Meta-governance is 5 of 7 plus 2 of 3 over 90 days, with a 30 day public comment. The tier 5 row is 5 of 5 over 180 days. This page does not choose between them.

The names in the roster file are placeholders. Keyholder activation is 5 of 7 and is a different pool from maintainer signatures. The governance-node quorum is 2 of 3 in a written set. That quorum is not the layer 5 maintainer signature, which is also 2 of 3 and applies to blvm-sdk.

How each institution row was counted

Each reading uses the history that tree actually has. Where the checkout is shallow, the count is the GitHub contributor total.

When enforcement is on, two of three governance nodes in a written set must each conclude that an action conforms before that action stands. Anyone may run a node and publish a conclusion. Only the written set binds. Changing that set is a Tier 5 governance-rule change. The two written Tier 5 pairs both remain.

Forms

These cards are the codebook from Bitcoin Has Governance. Each score is a judgment of a form, not a measurement of a tree. The order is the article's. A higher total is not a rank of the implementations above.

Capture resistance
The smallest set of actors whose assent changes the rules, and how concentrated merges are.
Exit cost
The share of economic weight that followed a fork. A higher score means leaving is cheaper.
Legibility
A named decider, and a written rule for who decides. Neither part scores 1. One part scores 2 or 3. Both score 4 or 5.
Error correction
Time from a bad decision to a rollback, and who had to agree.
Credible commitment
How many veto players there are, and how far apart they sit.
Decision cost
Time from proposal to decision. A higher score means the decision is cheaper.
